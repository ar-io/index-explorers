# Contributing

## Setup

Node 22 or later and pnpm (the version in `package.json`'s `packageManager`).

```bash
pnpm install
node scripts/fetch-engine.mjs      # caches the pinned Parquet extension for the fixture gateway
npx playwright install chromium    # for the E2E suites
```

## The ladder

Run these before opening a PR; CI runs the same.

```bash
pnpm lint          # prettier --check and every package's typecheck (TypeScript strict)
pnpm test          # Vitest: index-client (with native DuckDB over a recorded band), the apps' models
pnpm --filter "./apps/*" run build:e2e
pnpm e2e           # Playwright against the local fixture gateway: deterministic, no network
pnpm e2e:live      # the same suites against turbo-gateway.com (nightly in CI)
pnpm pins:check    # engine.lock.json against npm and two gateways
```

`pnpm e2e` writes screenshots and traces to `e2e/out/` (cleaned per run) and
the HTML report to `e2e/report/`. For anything you want to keep across runs,
write outside `e2e/out/`.

## Where things go

- Trust-critical code goes in `packages/index-client` and gets a unit test
  against a fixture. The library has no DOM except the service worker.
- Layout knowledge (file names, lookup keys, the SQL of a view) lives in
  `packages/index-client/src/layouts/`, never in an app.
- Apps keep one store, one session, pure models in `model/`, flows in
  `data/`, views as functions of the store. No module-scope state, no
  string-built DOM.
- Ids and classes the E2E suites use (`#proof`, `#find`, `#results`,
  `#b-list` …) are part of the acceptance contract; rename them in the
  tests too.

## Fixtures

`fixtures/live` is recorded from turbo-gateway.com (publication seq 159, its
registry, one small band and torrent). `fixtures/synthetic` is generated by
`pnpm fixtures:build`, deterministic, and committed with its outputs so CI
never depends on a DuckDB version writing identical bytes. Regenerate it only
when the generator changes, and commit the result in the same PR.

## Rules

- Never weaken a check to make a test pass. If the index or its docs look
  wrong, say so in the PR; the index and its tooling are maintained in
  ar-io/ar-io-node and gaps there are tracked upstream, not papered over here.
- Names from record JSON are labelled as not covered by the signature and
  size-checked against the index, wherever they appear.
- Measure before and after any change on the drive-browser path; the
  acceptance numbers are in V1-ARCHITECTURE.md §4.2 and in the PR
  descriptions.
- Never run the suites on a gateway: a gateway blocks its own public IP on
  `/raw`, so names fail there and nothing else is representative.

## PRs

Small, one concern each, with the numbers measured in headless Chromium in
the description when the change touches a listing path. Commit messages
follow conventional commits (`feat(index-client): …`, `fix(ardrive-explorer): …`).
Deploys happen only from a tag through the Deploy workflow, and only for a
release verified locally with `node scripts/release.mjs verify <app> --version <x.y.z>`;
see the README.
